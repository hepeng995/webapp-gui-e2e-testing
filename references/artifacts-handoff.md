# 产物沉淀与下游交接（artifacts-handoff）

执行报告完成后（或用户要求时）生成下列产物。核心思想（业界共识）：探索性/人工测试的发现要沉淀为**可重复执行的自动化资产**，否则价值随会话流失。

## 0. 标准产出目录结构（所有文件位置固定，禁止随意散落）

```text
<产出目录>/                          # 每轮测试一个目录（如 e2e-results-20260908/；续作沿用同一目录）
├── 测试用例文档-vN.md                # 摘要展示（非阻塞）产物：层级树(每级预期+来源)+十类用例+环境需求清单
├── pitfalls.md                      # 经验回写：项目级坑清单（跨轮累积，开工必读）
├── results/                         # 执行证据与报告
│   ├── 环境说明.md                  # 模式/端口/库/账号（"自补充记录"追加在此）
│   ├── BUG-<前缀>NNN.md             # BUG 单：唯一异常登记载体（缺陷/环境问题/文档差异/待确认），一单一文件
│   ├── 执行日报-<日期>.md            # 每日/每批次一份
│   ├── 执行报告.md                  # 收尾一份，统计以 summary 为唯一数据源
│   ├── <批次或L1模块>-结果.md        # 用例结果：按批次/L1 模块合并成文件，禁止每用例一文件
│   ├── summary.json / summary.csv   # 机器可读统计（跨轮对比基线）
│   ├── screenshots/                 # 全部截图（<用例编号>-<序号>-<语义>.png），唯一截图目录
│   └── logs/<用例编号>/             # console.log + network.md（FAIL/FLAKY 必有）
└── outputs/                         # 按需产物——无消费方时整个目录不生成
    ├── playwright/                  # spec 草稿（仅当用户有 CI/开发侧消费方）
    └── visual-baseline/<轮次>/      # 视觉基线截图（仅当用户圈定页面清单）
```

固定纪律：① 每轮一个产出目录，多轮对比靠 summary，不靠文件混放；② 用例文档、pitfalls 在产出目录根，证据与报告全在 `results/`，交接类全在 `outputs/`；③ 目录内不允许出现本树之外的临时文件（确需产生，收尾删除或移入 outputs 并在报告说明）。

## 1. 机器可读结果汇总（每轮必出）

- `results/summary.json` 与 `results/summary.csv`：每条用例一行——`编号、状态（PASS/FAIL/FLAKY/BLOCKED/SKIPPED/INTERRUPTED）、优先级、L1-L2 模块码、被测元素、关联缺陷、执行账号、耗时、环境模式（本地/网络）、前端/后端版本（commit 或构建号）、健康信号（flaky 次数、最近执行轮次、累计发现缺陷数）`；轮级字段（环境模式、被测版本）写入 summary 头部，结构见 `assets/templates/summary-template.json`。
- 执行报告的统计表以 summary 为唯一数据源，避免口径漂移；健康信号支撑报告"用例集健康"节（频繁 FLAKY / 长期未执行 / 高龄零发现）。
- **跨轮对比**：新轮次开工时读上一轮 summary 作基线，报告增加"跨轮对比"节——通过率变化、新增/闭环缺陷、上轮 FLAKY 本轮是否稳定、上轮 BLOCKED 本轮是否解阻；PERF 类数值对比仅在同环境模式下有效（本地与网络的网络耗时不可比，版本不同也要注明）。

## 2. Playwright 脚本草稿（按需，非默认产物）

**定位红线**：脚本草稿是**交接产物**，供 CI/开发侧后续接入使用；**禁止用脚本执行本轮验证**——一切验证结论必须来自 Agent 通过会话浏览器交互式执行的测试（SKILL.md §5 第 9 条），生成的脚本也不得回用于本轮。

**生成前提**：用户明确存在消费方（Playwright/CI 流水线、开发侧要可直接运行的复现脚本）时才生成；否则跳过。无 CI 接入的 Agent 桌面会话场景下，回归闭环靠"重跑 skill（冒烟集 + summary 跨轮对比）+ BUG 单复现场景"，默认不产出无人执行的脚本死资产。

生成时约定：

- 输出 `outputs/playwright/`：把关键 PASS 用例（P0 主链路优先）与缺陷复现场景转为 Playwright spec 草稿。
- 定位器直接复用执行期记录的**成功定位方式**（execution-loop §1），选择器自带 fallback 注释。
- 失败/未验证的用例转 spec 时标 `test.fixme` 并注明原因；每份草稿头部注明"未经 CI 验证，需开发侧跑通后入库"。
- 缺陷复现场景优先转换（对应"把发现转化为最便宜的可靠层"）：修复回归后即可挂入 CI 防复发。

## 3. 轻量视觉基线对比（可选，按用户圈定范围）

- 摘要展示时圈定关键页面清单（建议 L1 主页面 + 高风险视觉页）。
- 每轮对清单页面截图存档 `outputs/visual-baseline/<轮次>/`（固定视口与数据态，动态内容如时间戳/头像区先遮罩或裁剪）。
- 下轮用脚本环境（Python/Pillow 或 Node）跑像素 diff，差异超阈值（建议默认 1% 像素）标记人工复核；内置浏览器只负责截图与查看，diff 在脚本环境执行。
- 基线更新需用户确认（记录在 summary 或报告）。

## 4. 经验回写闭环

- 每轮收尾把新发现的坑回写项目级坑清单 `pitfalls.md`（P 编号+现象+规避手段，跨轮累积，开工必读）；缺陷修复并回归后及时在坑清单标注"已修复"，避免后续测试绕过已不存在的问题。
- 开工预检必读坑清单（environment.md §3）；已修复的坑及时标注，避免后续测试绕过已不存在的问题。

## 5. 失败结果的完整留痕（强制，与 evidence.md 联动）

任何 FAIL/FLAKY 的用例结果必须当场包含四件套，不允许"先记 FAIL 后补证据"：

1. 失败时刻截图（evidence.md §1.2）；
2. console/network 错误日志路径 + 关键报错摘要（evidence.md §2.2）；
3. 复现步骤（六要素精简版：账号+入口 URL+步骤）或 BUG 单号；
4. 已尝试的定位方式与最终成功定位（execution-loop §1）。
