# 测试用例与环境需求生成（test-case-generation）

适用：开始测试前，基于**项目代码与文档**生成测试用例文档和测试环境需求清单，展示摘要（非阻塞）后进入执行。方法论参考 ISO/IEC 25010 质量模型（功能/性能/兼容/易用/安全等特性）与"解析代码+文档 → 生成结构化用例 → 人工确认闭环"的 AI 用例生成实践。

## 1. 输入采集

| 来源 | 采集什么 | 采集深度 |
| --- | --- | --- |
| 项目代码 | 路由/页面清单（**含嵌套与动态路由的全量叶子路由**）、页面内子界面（tab/弹窗/抽屉/折叠面板）、API 路由、数据模型（schema/实体）、**权限模型（角色/守卫/鉴权）**、组件目录、**跨模块跳转与联动引用** | 读结构与关键文件即可，不逐行精读 |
| 项目文档 | PRD/功能说明、API 文档、数据库文档、设计规范、既有测试文档 | 全读 |
| 用户补充 | 重点关注模块、已知风险、本次版本变更范围（回归基线） | 缺省时询问或按代码推断 |

## 2. 生成步骤

1. **建立被测对象层级树**（四级，罗列到最小颗粒度元素）：

   | 层级 | 含义 | 示例 |
   | --- | --- | --- |
   | L1 模块 | 业务大模块 | 订单中心（ORD）、商品管理（PROD） |
   | L2 页面/子功能 | 模块内的页面或子功能 | 订单列表页（LIST）、订单详情页（DETAIL）、创建抽屉（CREATE） |
   | L3 功能区 | 页面内的功能区/组件 | 筛选栏（FILTER）、列表表格（TABLE）、分页器（PAGER）、状态选择器 |
   | L4 元素 | 最小颗粒度：单个输入框/按钮/链接/弹窗/toast/列 | 搜索输入框、搜索按钮、状态下拉、每条操作列按钮 |

   树上**每一级都必须标注预期效果与来源**（L1 模块级业务预期、L2 页面级职责预期、L3 功能区级交互预期、L4 元素级正确行为），预期来源按下方规则确定，禁止无来源的"想当然"。L4 元素另标注适用的测试类型（F/U/C/P/S/A/D/E/R/Us 勾选，Us=易用性）。L1/L2 取英文缩写作为模块码（如 `ORD-LIST`）。

**层级树深挖规则**（禁止只按一级菜单/路由建树，必须挖到叶子视图）：

1. **路由全量**：从路由配置提取全部叶子路由——嵌套路由、动态路由（`/orders/:id`）、菜单外的深链页/设置页/异常页（403/404）都要入树；
2. **页面内子界面**：tab 页、折叠/展开面板、抽屉、弹窗、向导分步——每个可切换出现的子视图都建 L2/L3 节点；需要交互才出现的界面同样入树，标注"交互触发"；
3. **隐藏入口**：下拉菜单、"更多"按钮、行内展开等入口指向的界面逐一展开，不因入口隐蔽而漏建；
4. **跨模块关联**：按下文"关联分析"六维方法系统执行——不是想到才测，而是逐维过一遍，这是用例完整性的关键；
5. **挖掘手段**：路由配置 + 菜单/导航组件 + 页面组件目录 + 跳转调用（navigate/link/router.push）互相印证；静态看不全的（动态菜单、后端下发路由）用探索性打开页面实测补全，发现即回填层级树（纯 URL 黑盒场景无代码可读，探索实测即主要手段，见 test-planning.md §4 路径 D）。

**关联分析（跨模块/跨功能，建树后强制执行——决定用例完整性的关键步骤；融合开源方法：数据流/CRUD 矩阵、Google Test Analytics 的 ACC 能力矩阵、组合交互测试 CIT/pairwise、用户旅程编织）**：

1. **实体 CRUD 矩阵（数据耦合）**：列出全部业务实体（订单、商品、用户、权限…），矩阵标注每个模块对每类实体的 C/R/U/D（从代码的 API 路由 → 数据模型推导）。判定规则：
   - 实体被 ≥2 个模块**写入** → 一致性与并发冲突用例（双入口改同一数据：后写覆盖还是提示冲突）；
   - 实体被 ≥2 个模块**读取** → 展示口径一致性用例（同一实体在不同页面的状态徽章/计数/字段格式一致）；
   - 实体有**删除/归档**操作 → 引用完整性用例（A 模块删除后 B 模块列表/详情/统计的行为：消失/占位/报错）。
2. **跨模块能力（ACC 能力矩阵）**：Capability = 用户可感知的端到端行为（如"下单后库存与报表同步"），逐个标注横跨哪些模块；凡横跨 ≥2 模块的能力必须生成关联用例——**禁止只测发起方、不验证受影响方**。
3. **事件流分析（行为耦合）**：枚举每个写操作对外产生的事件（通知、待办、消息、缓存失效、列表/KPI 刷新），画"A 模块 --事件--> B 模块"流；每条流生成"A 侧操作 + B 侧断言（内容正确 + 及时性）"用例。
4. **共享资源分析（实现耦合，代码信号）**：从代码提取共享点——多模块调用的同一 API 端点、读写的同一数据库表、复用的同一前端组件/hooks/工具函数、同一枚举字典/配置。每个共享点登记为回归敏感区（RCRCRC 的 Risky/Chronic 候选）并生成一致性用例。
5. **状态机联动**：一实体的状态作为另一功能的前置门槛或触发器（如"订单已支付"才能发货、"审批中"禁止编辑），逐条状态-门槛关系生成联动用例（前置状态 + 门槛行为两侧断言）。
6. **用户旅程编织（E2E 场景）**：把 P0 主流程串成跨模块旅程（登录→创建→流转→审批→通知→统计报表），每条旅程一个端到端用例，重点断言**模块交接处**的数据与状态传递。

配套规则：

- **关联用例编号**：`TC-<类型码>-CROSS-<NNN>`（CROSS 作模块码），断言分别落到各侧 L4 元素，与模块内用例统一统计；
- **组合爆炸裁剪（pairwise/CIT）**：关联用例涉及多因素组合（实体 × 状态 × 角色 × 入口）时按两两组合覆盖裁剪，不逐组合全展开；被裁掉的组合在"未覆盖面与原因"注明；
- **纯 URL 黑盒降级**：无代码可读时，推导手段改为**网络观察 + 页面探索**——CRUD 矩阵从各页面操作触发的请求推导（POST/PUT/DELETE=写、GET=读，同一资源出现在多页面请求=跨模块读写）；共享资源=多页面调用同一 API 端点；事件流=操作后切换页面观察可见变化（通知/待办/列表刷新）；状态联动=状态徽章与按钮可用性的对应关系；推导结论一律标注"依据网络观察"；
- **关联覆盖自查（强制）**：每个 L1 模块必须出现在至少一条关联中（CRUD 矩阵行/ACC 能力/事件流/状态联动/旅程）；确实无关联的标注"独立模块"并写理由。关联分析产物（矩阵表 + 关联清单）作为用例文档必附节（模板 §1.3），摘要展示时一并汇报关联用例数。

**预期效果确定规则**（每条预期必须可溯源，禁止无来源的"想当然"）：

| 优先级 | 来源 | 处理方式 |
| --- | --- | --- |
| 1 | 文档明确写了 | 预期=文档描述，标注来源章节（如"文档 03 §3.2"） |
| 2 | 文档缺失/含糊，代码行为明确 | 预期=代码实际行为，标注"依据代码"；若与文档矛盾，同时登记"文档差异" |
| 3 | 文档与代码都无法唯一确定（含纯 URL 黑盒场景） | 先按**黑盒预期来源**取用：a) 页面自身声明（按钮/提示/帮助文案承诺的行为）；b) 平台常识惯例（提交有反馈、删除有确认、必填有标注、错误提示可读）；c) 全站一致性（同语义元素在本系统其他页面的一致行为）——取到即用并标注"依据声明/惯例/一致性"；仍定不了标 `预期待确认`，汇入"待确认预期清单"，**自动裁决**：有建议候选的采用建议（标"自动裁决：建议"），无建议的按代码实际行为、无代码时按惯例默认（标"自动裁决：依据代码/惯例"）；每条附候选与选择依据（如"A：Enter 触发搜索 ✓ / B：须点搜索图标"），裁决结果在摘要中展示并留痕，用户可事后纠正 |
| 4 | 用户事后纠正了自动裁决 | 预期回填（来源："用户 <日期>"），受影响用例重测；确实无法稳定观察预期的用例照常执行，结论记"行为观察"（不判 FAIL/PASS），开"待确认"类 BUG 单 |

**账号矩阵按需判定**（按代码实际权限模型决定，不默认要求多账号）：

| 代码探测结果 | 账号矩阵口径 |
| --- | --- |
| 无权限体系（无角色/权限字段、无路由守卫、API 无鉴权差异） | 单账号执行全部用例；权限可见性/越权类用例标"不适用"，依据写"代码无角色与权限区分" |
| 有权限体系 | 从代码提取**实际存在的角色集合**（角色枚举、权限配置、路由守卫、后端鉴权中间件），按实际角色生成矩阵，不套用固定角色清单；水平/垂直越权用例按实际角色对生成 |
| 探测不确定（鉴权在网关/外部服务） | 按有权限体系保守处理，探测结论标"待确认" |

判定依据（守卫文件、角色字段、权限配置）与最终角色清单写入 §5 环境需求清单"账号矩阵"行；需要多角色而网络测试环境缺账号时，询问用户获取。

2. **从层级树生成用例**：用例挂在 L2/L3 层级、断言落到 L4 元素及其预期效果；同一元素按标注的类型生成多条用例（编号 `TC-<类型码>-<L1>-<L2>-<NNN>`，如 `TC-FUNC-ORD-LIST-001`）。纯展示类元素的简单断言（存在/文案/颜色语义）合并为该元素的**检查清单行**（每行带预期与来源），不单独成用例；涉及流程或组合行为的升级为独立用例。

**用例步骤书写规范**（融合关键字驱动 KDT 的动作词结构、BDD/Gherkin 的操作→断言结构、业界颗粒度共识；决定步骤能否被独立照做）：

1. **每步三要素**：动作词（点/输入/选择/切换/勾选/滚动/上传）+ 操作对象（精确到 L4 元素，用页面可见文案或 testid 表述）+ 测试数据（具体值，新建数据带本轮前缀）。示例：`2. 在[搜索框]输入"E2E-DEMO-01 订单号"`；禁止"测试搜索功能"这类无对象、无数据的步骤。
2. **步骤级观察点（When→Then）**：写操作、状态跳转、提交类步骤后紧跟 `→ 预期：<该步观察断言>`（UI 变化或网络断言），与用例结果记录的"步骤 → 断言"结构一一对应；纯导航步骤可不挂。
3. **颗粒度分级**：一个功能点一条用例（不重复、不冗余）；步骤以 3-8 步为宜——主流程用例 3-5 步，超出 10 步说明该按功能点拆分；前置条件（账号/数据/入口）写在"前置"字段，不混入步骤。
4. **用户视角表述**：步骤只写"用户看到什么、做什么"，不写系统内部实现（与黑盒执行底线对齐）；步骤编号可独立照做，执行循环逐步核对勾选。

3. **数量原则**：功能类每模块覆盖主流程+主要分支；UI/UX 按覆盖维度矩阵逐模块过一遍；安全/异常按风险全列出抽测面。**宁全勿漏**，按优先级执行（P0 先行，预算不足时低优先级自然收束），用户可在任何时候补充或裁剪，不在生成时偷减。
4. **汇总测试环境需求清单**（§5）。
5. **展示用例摘要**（§4，非阻塞），随即进入环境准备与执行。

## 3. 十类测试（类型码固定，报告与统计按此口径）

| 类型 | 码 | 生成要点 | 主要依据 |
| --- | --- | --- | --- |
| 功能测试 | FUNC | 主流程、CRUD、业务规则、权限可见性 | PRD 功能点、路由与 API 清单 |
| UI/UX 测试 | UIUX | 页面五态、观察六维、一致性巡检、布局样式 | coverage-dimensions §1/§2/§11 |
| 兼容性测试 | COMP | 视口 375/768/1440、200% 缩放、移动外壳；浏览器引擎受限于内置浏览器，用例中写明"仅当前引擎+视口/尺寸兼容" | coverage-dimensions §8 |
| 性能测试 | PERF | 首屏与路由加载耗时、大列表分页、大文本/大附件、慢请求识别（轻量测量：记录耗时数值与感知卡顿，不做专业压测） | 观察六维 + 网络记录 |
| 安全测试 | SEC | 越权（水平/垂直）、直连 URL 不泄露数据、注入类输入、敏感信息泄露、会话过期/固定 | coverage-dimensions §4 + 数据攻击 §3 |
| 接口测试 | API | 经 UI 触发的请求合同：方法/路径/关键 body/幂等键/错误码/UI 与服务端状态一致性；API 读回核对 | 断言三类 |
| 数据测试 | DATA | 边界值、必填/唯一性、持久化（刷新后仍在）、并发修改冲突、删除级联、筛选/排序/统计口径 | coverage-dimensions §3/§12 |
| 异常场景 | EXC | 请求失败/断网、重复提交、会话过期、操作中断恢复、空数据、依赖服务异常 | coverage-dimensions §5 |
| 易用性测试 | USE | 操作路径长度、提示可理解性、错误可恢复（不丢已填内容）、快捷键/回车行为可见性 | coverage-dimensions §6/§11 |
| 回归测试 | REG | RCRCRC 圈定：核心链路+近期改动+已修复缺陷复测+惯犯区域 | test-planning §5.3 |

> 黑盒边界提示：接口类与性能类在 GUI 黑盒下的实现方式 = UI 触发 + 网络观察 + API 读回；禁止为接口测试直接调写接口造数据（ preparation 阶段除外，见 environment.md）。

**维度按项目代码定制**：十类不是固定等权清单——生成阶段先从代码结构推导适用性（无上传组件→文件类攻击不适用；无富文本→粘贴图片不适用；有工作流/状态机→状态转换维度必选；有导出→大数据量导出必选），并可增补项目特有维度；定制结论（适用/不适用/新增维度及理由）写入用例文档"未覆盖面与原因"节。PERF 类统一用 coverage-dimensions §8 的只读性能度量动作；SEC 类先做 §4 只读基线（响应头+敏感信息扫描），深度攻击标人工/专项。

## 4. 用例摘要展示（非阻塞，生成后立即执行）

生成用例文档后，**向用户展示简短摘要，随即进入环境准备与执行，不停下等待确认**（自动化优先；用户明说"先确认再跑"时才阻塞等待确认）：

```markdown
【用例文档摘要】共 N 条用例：
| 类型 | 用例数 | 覆盖模块 | 其中 P0 |
| 功能 | x | … | x |
| …（十类逐行列出，0 条的也要列出并写明原因）|
环境需求摘要：<库/账号/seed/配置一句话>
未覆盖面：<模块/维度 + 原因>
待确认预期自动裁决：<逐条：元素 → 采用的候选 + 依据>
（摘要展示完毕，继续准备环境并执行；需补充或纠正随时提出，已执行且结论受影响的用例按补充重测）
```

- 待确认预期**自动裁决留痕**：裁决结果（元素、采用值、依据、日期）写入用例文档头部；用户事后纠正时回填（来源："用户 <日期>"）、版本号 +1，受影响用例重测；
- 用户随时补充/纠正 → 并入文档、版本号 +1，继续执行；
- 用户明说"先确认再跑" → 恢复阻塞模式：展示摘要并等待确认后才执行。

## 5. 测试环境需求清单（用例文档必附节）

| 需求 | 内容 | 依赖用例 |
| --- | --- | --- |
| 服务拓扑 | 前端/后端/数据库地址与端口 | 全部 |
| 库与数据 | 迁移/基线、seed、前置单据状态 | 指定编号 |
| 账号矩阵 | 角色 × 登录方式 × 权限语义 | 指定编号 |
| 配置项 | 开关、环境变量、mock 依赖 | 指定编号 |
| 工具能力 | 上传/拖拽/console 监听等 | 指定编号 |

每项标注依赖它的用例编号——测试中缺什么，能立刻定位影响面。

## 6. 执行中的环境自补充（授权 + 强制记录）

测试过程中发现缺少测试环境（缺账号、缺前置数据、缺配置、服务未起、缺 mock）：**允许自行补充**，规则：

1. **记录**：补充动作追加到 `环境说明.md`（"自补充记录"节：时间、补了什么、方式、服务于哪些用例）+ 当日执行日报；
2. **不得替代被测行为**：测创建流程不能直接插一条现成数据当结果；补充只负责"让被测功能可达"；
3. **状态联动**：因补充解阻的用例（BLOCKED→可执行）在用例结果中注明"经环境补充后重测"；
4. **红线**：禁止为通过用例修改产品代码、禁止篡改数据库既有业务数据、禁止把缺陷现场"修好"（那是修复缺陷，需用户授权，走 issue-tracking 流程）。

## 7. 权威清单差异补全模式

已有权威用例清单时（如既有项目的固化清单）：本阶段不生成全量用例文档，改为**差异补全**——扫描代码与文档，找出权威清单未覆盖的模块/新功能/新接口，按十类生成补充用例（编号 `TC-SUP-<模块>-NNN` 与权威清单区分），摘要展示与环境需求清单同样适用。
