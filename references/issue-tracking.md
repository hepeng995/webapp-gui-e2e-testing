# 问题登记与缺陷管理（issue-tracking）

原则：**宁多勿漏**。执行期间发现的一切异常都开 BUG 单登记，不限于导致用例失败的问题；用例 PASS 也要记录过程中的顺带发现；无法判定的按"待确认"登记，禁止自行忽略。**BUG 单是唯一异常登记载体，不再设独立问题清单。**

## 1. 发现记录三分法

记录现象时区分三个层次，防止把推断写成事实：

- **Observation 观察**：实际看到/读到的（文案、状态码、网络记录、截图）——写事实。
- **Inference 推断**：由观察推出的判断（初步定位、影响分析）——标注"初步定位/推测"。
- **Question 疑问**：无法判定的（是否为设计内行为、是否与文档一致）——按"待确认"类 BUG 单登记。

文档与实际不符时：以代码/实际行为为准继续执行，差异开"文档差异"类 BUG 单。

## 2. BUG 单（`results/BUG-<前缀>NNN.md`，唯一登记载体）

一切异常开 BUG 单，用**类别**字段区分四类：

| 类别 | 定义 | 后续动作 |
| --- | --- | --- |
| 缺陷 | 实际行为与文档/预期不符（含顺带发现：错别字、样式错位、徽章颜色、空态缺失、计数可疑、文案未本地化） | 走缺陷生命周期（§3） |
| 环境问题 | 环境/账号/数据/工具故障（服务起不来、seed 不兼容、端口占用、上传服务异常） | 修复或绕过说明；缺环境可自行补充，补充动作必须记录（environment.md §6）；环境恢复验证后闭环 |
| 文档差异 | 测试文档与代码实际不符 | 按实际执行，日报汇总；核对确认后闭环 |
| 待确认 | 疑似问题但证据不足以判定 | 禁止丢弃；报告中单列请人工复核；裁决后转"缺陷"或标"已排除（依据）" |

- 每张单必填：编号、时间、类别、关联用例（或"过程发现"）、现象摘要、复现要点（URL+步骤）、证据（截图/console/网络至少其一）、状态。
- 编号规则：`BUG-<前缀><三位序号>`（如 `BUG-A1-001`）；多 Agent 并行时前缀互不混号（见 multi-agent.md）。
- **登记深度按类别伸缩**：缺陷类必须写全六要素复现场景（evidence.md §3）；环境问题/文档差异/待确认类"复现场景"节精简为入口 URL + 步骤摘要即可，孤立 console warning 等轻微发现同样精简登记，不为凑格式增加负担。

## 3. BUG 单生命周期（缺陷类）

```
新建 → 待修复 → [外部追踪系统映射（可选）] → 修复 → 回归验证 → 闭环
```

- 缺陷是否修复、何时修复由用户/负责人决定，测试方只负责如实记录与回归验证。
- 修复后必须按 BUG 单原复现场景回归：结果与证据追加在 BUG 单"回归验证记录"段；PASS 才闭环，仍 FAIL 退回并注明。
- 用户/负责人明确决定不处理的缺陷：状态标 `WONTFIX（决定人+日期）`，保留单据，不得删除。
- 环境问题/文档差异/待确认类不走修复回归流程：环境问题在环境恢复后验证关闭；文档差异核对后关闭；待确认经裁决转缺陷（走生命周期）或标"已排除（依据）"。

## 4. 与外部追踪系统的映射（可选）

用户要求登记到工单系统（Teambition/Jira 等）时：在 BUG 单追加"外部单号"行；同根因可合并为一张外部单，映射表放执行报告；合并后每张原 BUG 单都要能通过映射表找到归宿。仅"缺陷"类需要映射，其余类别不外发。
